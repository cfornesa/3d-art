# Figure Opacity and Layering Bug Fix

## Problem Statement
Two rendering bugs reported:
1. **Opacity: 0 makes layer appear 100%** (fully opaque appearance instead of invisible)
2. **Layer interaction fails** — figures below transparent figures disappear or "pierce through" incorrectly

## Root Cause Analysis

### Bug 1: P5.js ignores opacity completely
In `src/libraries/p5.js`, the `_drawFigure()` method (lines 176-239) does **not** apply any opacity. There's no `p.globalAlpha` call, so all shapes draw at full opacity regardless of the figure's opacity value.

### Bug 2: Three.js transparent objects block depth buffer
In `src/libraries/three.js`:
- Line 150: `transparent: figure.opacity < 1.0` — correctly marks transparent materials
- Line 151: `opacity: figure.opacity !== undefined ? figure.opacity : 1.0`
- **Missing**: `depthWrite: false` for transparent objects

When a transparent object has opacity 0, it's still rendered and **writes to the depth buffer**, causing objects behind it to be culled even though the object itself is invisible.

### Bug 3: C2 renderer is correct
C2 properly sets `ctx.globalAlpha` (line 138) before drawing.

---

## Implementation Options

### Option A: Direct Fix (Recommended)
Fix the two bugs in place:
1. **P5.js**: Add `p.globalAlpha(figure.opacity !== undefined ? figure.opacity : 1.0)` in `_drawFigure()`
2. **Three.js**: Add `depthWrite: false` for all transparent materials

### Option B: Reframe — Treat opacity: 0 as invisible shortcut
Instead of rendering a 0-opacity object that happens to be invisible, skip rendering it entirely when opacity is exactly 0. This is cleaner and more performant.

### Option C: Unexpected — Add depth management UI
The user might be experiencing an edge case where layer ordering doesn't match expected visual stacking. Could add a "depth test" toggle per figure for advanced users.

---

## Recommendation
**Option A** — Direct fixes address the stated bugs without behavioral changes. Option B is conceptually cleaner but changes semantics (0 opacity becomes "not rendered" vs "rendered but invisible"), which could break existing artwork configurations.
