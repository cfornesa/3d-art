# Fixes for Layer Ordering, Opacity 0, and Opacity 1 Rendering Bugs

## Current Problem Summary

| Issue | Renderer | Current Behavior | Expected Behavior |
|-------|----------|------------------|-------------------|
| Layer ordering | FigureManager | New figures placed below selected figure | New figures placed above selected figure |
| Opacity 0 | All | Appears at 100% opacity | Fully invisible (not rendered) |
| Opacity 0.9 vs 1.0 | Three.js | Opacity 1.0 "pierces through" incorrectly | Consistent rendering for all opacity values |

---

## Root Cause Analysis

### 1. Layer Ordering Bug (`figure-manager.js`)

**Problem in `createDefaultFigure()`**:
```javascript
if (selectedFigure) {
    newLayer = (selectedFigure.layer || 0) + 1;
    // Bump up all figures that are at or above this layer
    for (let i = 0; i < this._figures.length; i++) {
        if (this._figures[i].layer >= newLayer) {
            this._figures[i].layer++;
        }
    }
}
```

The bumping logic causes duplicates: If layers are [0, 1, 2] and we select figure at layer 1:
- newLayer = 2
- Bump layers >= 2 → [0, 2, 3]
- New figure gets layer 2 → Result: [0, 2, 3, 2] with duplicate layer 2

The selected figure ends up BELOW the new figure visually.

**Fix**: Simplify - always place new figure at `maxLayer + 1` (top), ignoring selection for placement. Selection is only for highlighting, not for insertion point.

### 2. Opacity 0 Bug

**P5.js** (`p5.js:182-183`):
```javascript
const opacity = parseFloat(figure.opacity);
if (!isNaN(opacity) && opacity <= 0) return;
```
This early return happens BEFORE `p.push()`, but after we've already potentially used `opacity` in a non-number state. The logic is correct but must verify figure.opacity is actually being read.

**Three.js** (`three.js:152-155`):
```javascript
if (finalOpacity <= 0) {
    return null;
}
```
This correctly returns null to prevent object creation. However, when `setFigures()` is called, if we previously had a figure with opacity 0 that was skipped, but then we call `setFigures()` again, the old object might still exist in the scene.

**Verification needed**: Is `figure.opacity` actually a number 0, or could it be `undefined`, `"0"`, or `null`?

**Fix**: Add console logging temporarily to verify actual opacity values, then ensure strict number comparison.

### 3. Opacity 1.0 vs 0.9 Rendering Bug (Three.js)

**Current approach**:
```javascript
const material = new THREE.MeshStandardMaterial({
    color: color,
    transparent: true,
    opacity: finalOpacity,
    depthWrite: !isTransparent,  // isTransparent = finalOpacity < 1.0
});
```

For opacity 1.0: `depthWrite: true` (writes to depth buffer)
For opacity 0.9: `depthWrite: false` (doesn't write to depth buffer)

**Problem**: When a transparent object is on top of an opaque object with `depthWrite: true`, the opaque object's depth contribution affects what's visible through the transparent object.

**Alternative fix needed**: For fully opaque (1.0), we could use `transparent: false` which is more efficient and renders differently. But earlier we found this causes inconsistency...

**Better approach**: Use `THREE.MathUtils.clamp(finalOpacity, 0.001, 1.0)` to avoid edge cases at exact 0 and 1 values.

## Implementation Plan

### 1. Fix Layer Ordering (`src/figures/figure-manager.js`)

Replace `createDefaultFigure()` bumping logic with simple top placement:

```javascript
FigureManager.prototype.createDefaultFigure = function() {
    const defaults = {
        three: { type: 'box', library_data: { castShadow: true, receiveShadow: true } },
        p5: { type: 'rect', library_data: { mode: 'center' } },
        c2: { type: 'rectangle', library_data: { fill: true, stroke: true } },
    };

    const libraryDefaults = defaults[this._library] || defaults.three;

    // Simply place at top (highest layer + 1)
    const maxLayer = this._figures.reduce(function(max, f) {
        return Math.max(max, f.layer || 0);
    }, -1);

    return window.DataToArt.FigureBase.create({
        type: libraryDefaults.type,
        name: 'Figure ' + (this._figures.length + 1),
        color: '#c9922a',
        library_data: libraryDefaults.library_data,
        layer: maxLayer + 1,
    });
};
```

Remove the selection-based insertion logic entirely.

### 2. Fix Opacity 0 Handling (All Renderers)

**P5.js**: Ensure strict number type checking
**Three.js**: Add null check and use `=== 0` instead of `<= 0` for exact match
**C2.js**: Verify same approach

### 3. Fix Opacity 1.0 vs 0.9 (Three.js)

**Option A**: Clamp opacity values to avoid exact 0 and 1:
```javascript
const finalOpacity = !isNaN(opacity) ? THREE.MathUtils.clamp(opacity, 0.001, 0.999) : 1.0;
```

**Option B**: Use different rendering path for full opacity:
```javascript
if (finalOpacity >= 1.0) {
    // Use opaque rendering
    material.transparent = false;
    material.depthWrite = true;
} else if (finalOpacity <= 0) {
    return null; // Don't create
} else {
    // Use transparent rendering
    material.transparent = true;
    material.depthWrite = false;
}
```

**Option B is recommended** - it uses the most appropriate rendering path for each case.
